# 万能导入 V2 技术方案

> 日期：2026-06-06  
> 项目：智能多格式批量下单系统 / 万能导入 V2  
> 适用范围：Excel / Word / PDF / CSV 任意格式批量下单导入  
> 目标环境：Next.js + Vercel + Prisma Postgres

---

## 1. 项目目标

围绕物流/快递行业“客户文件格式极不统一、但必须高效批量下单”的核心痛点，建设一个可在线访问的 Web 应用，完成以下目标：

1. **任意格式导入**：支持 Excel / Word / PDF / CSV，多结构、多噪音、多版式文件。
2. **大模型介入解析**：不再依赖固定模板或硬编码映射，由 LLM 基于样本结构生成可复用解析规则。
3. **鲸天系统风格统一**：界面视觉、布局、交互节奏保持鲸天系统一致，降低业务人员学习成本。
4. **高性能可落地**：在大批量导入场景下，上传、分析、解析、预览、提交全过程保持可接受响应时间。
5. **线上可访问**：部署至 Vercel，形成可演示、可验收、可持续迭代的在线版本。

---

## 2. 相比 V1 的核心变化

### 2.1 UI 不再是“能用即可”，而是必须“像鲸天系统”

V2 的 UI 目标不是普通后台，而是：

- 顶栏、侧边栏、内容区结构与鲸天系统保持一致
- 颜色体系、按钮风格、表格密度、弹窗样式统一
- 用户操作路径符合真实业务后台习惯
- 导入流程看起来像鲸天系统中的一个正式业务模块，而不是独立工具页

### 2.2 解析方式从“模板匹配”升级为“LLM + 规则引擎”

V1 更偏向固定列映射和有限模板识别；V2 必须支持：

- 干扰性头部信息
- 横向字段 / 矩阵型结构
- 合并单元格
- 多 Sheet / 多页 PDF
- 卡片式、半结构化、非标准表格
- 文本块中抽取收货信息、订单信息、SKU 信息

因此 V2 采用：

**文件样本提取 → LLM 生成规则 JSON → 用户确认 / 修订 → 规则引擎解析 → 校验 / 预览 / 下单**

### 2.3 性能目标从“能跑”升级为“可批量稳定使用”

不仅要支持大文件，还要在交互层面让用户感知为“顺畅”：

- 大文件上传不能卡住页面
- 解析过程必须有进度反馈
- 预览 1000+ 行不能卡表格
- 重复检测、分页、历史查询要可扩展
- Vercel 环境下要避免超时和内存浪费

## 3. 业务问题拆解

用户提供的源文件通常存在以下特征：

1. **格式不统一**：同一客户不同时间的文件可能结构不同。
2. **字段命名不统一**：如“收货人 / 门店 / 客户名称 / 到货方”可能都指向收件对象。
3. **表格结构不标准**：有合并单元格、空行、说明文字、合计行、分页头。
4. **字段不完整**：部分文件只有门店信息，没有标准收件人三要素。
5. **文件内容跨区域分布**：商品明细在中间，收货信息在页脚或页眉。
6. **量大且实时性要求高**：常见 100~1000 单批量导入，不允许长时间等待。

因此系统必须具备两种能力：

- **结构理解能力**：识别文件“长什么样”
- **业务容错能力**：识别“这份文件在物流场景下想表达什么”

## 4. 总体技术架构

建议采用 **“前端交互层 + 文件解析层 + LLM 规则层 + 规则执行层 + 数据持久层”** 五层架构。

### 4.1 架构分层

#### A. 前端交互层（Next.js App Router）
负责：

- 上传文件
- 展示 AI 分析结果
- 规则确认 / 编辑
- 解析进度反馈
- 结果预览 / 校验提示
- 历史批次与规则管理

#### B. 文件解析预处理层
负责从不同文件中提取“适合给 LLM 理解的样本”：

- Excel：Sheet、行列、表头样本、矩阵结构
- PDF：按页文本、表格块、坐标文本
- Word：段落、表格、文本块
- CSV：文本行样本

#### C. LLM 规则生成层
负责把样本转换为结构化解析规则 JSON：

- 识别 parser.type（table / matrix / card / text / multi-sheet / multi-page / double-matrix）
- 输出字段映射、正则、行列范围、收件人抽取规则
- 标注 confidence / inferred / reason，告诉用户哪些字段是推断

#### D. 规则执行层（Parse Engine）
负责把规则真正落到文件解析：

- 根据 parser.type 调用不同解析器
- 统一输出 ParsedOrder[]
- 执行业务校验、重复检测、来源追踪

#### E. 数据持久层（Prisma Postgres / Neon）
负责持久化：

- 解析规则库 parse_rules
- 导入批次 import_batches
- 导入订单 import_orders
- 后续可扩展学习样本、解析反馈、规则命中率

## 5. 解析链路设计

### 5.1 标准主流程

1. 用户上传文件
2. 前端识别文件大小与类型
3. 系统选择处理策略：
   - 小文件：直接上传解析
   - 大文件：Worker 预处理 / 分片上传
4. 后端提取样本
5. 调用 LLM 生成推荐规则 JSON
6. 前端展示规则 + 样本预览 + 置信度提示
7. 用户确认规则或手工调整 JSON
8. 规则引擎执行解析
9. 结果校验（必填、重复、异常）
10. 用户预览确认
11. 保存批次 / 订单
12. 进入下单链路或历史查询

### 5.2 两阶段解析策略

建议明确采用 **“分析阶段”** 与 **“执行阶段”** 分离的设计：

#### 阶段 1：AI 分析阶段
目标：理解结构，不直接产生最终订单。

输入：文件样本  
输出：推荐规则 JSON

特点：
- 调用 LLM
- 耗时不稳定
- 结果可能存在推断项
- 可以人工复核

#### 阶段 2：规则执行阶段
目标：按规则快速稳定产出订单数据。

输入：完整文件 + 已确认规则  
输出：标准化订单数组

特点：
- 不依赖 LLM 实时参与
- 可重复执行
- 更快、更稳定、更可测试
- 适合大批量解析和生产环境复用

**这是整个方案最关键的架构决策。**  
LLM 负责“理解”，规则引擎负责“执行”。这样既保留任意格式能力，又避免每次导入都被大模型性能和波动牵制。

## 6. 规则 DSL 设计建议

当前项目已经具备较成熟的规则 JSON 思路，建议继续固定为 DSL，而不是让模型输出代码。

### 6.1 顶层结构

```json
{
  "name": "规则名称",
  "description": "规则说明",
  "fileTypes": ["excel"],
  "identifier": {
    "fileNamePattern": "...",
    "headerKeywords": ["..."],
    "sheetCount": 1,
    "minRows": 1,
    "minCols": 1
  },
  "parser": { ... },
  "recipient": { ... }
}
```

### 6.2 parser.type 建议保留并扩展为

- `table`：标准行列表格
- `matrix`：SKU × 门店矩阵
- `double-matrix`：门店 × 日期 / 单元格拆分物品数量
- `card`：卡片 / 单据块结构
- `text`：纯文本 / 正则提取
- `multi-sheet`：多 Sheet 汇总
- `multi-page`：多页 PDF 拆单

### 6.3 为什么必须是 DSL

因为 DSL 有四个优势：

1. **可审查**：用户和开发都能看懂规则，不是黑盒。
2. **可编辑**：规则可以被手工修正，而不是重新训练。
3. **可沉淀**：同类客户文件可以保存为长期规则资产。
4. **可测试**：规则和样本可做回归验证。

## 7. 文件类型解析策略

### 7.1 Excel / CSV

适合处理：

- 标准表格
- 多 Sheet 表格
- 横向矩阵
- 合并单元格弱规范文件

建议：

- 读取原始二维数组而非仅依赖表头行
- 允许识别空行、备注行、合计行
- 对“合计 / 总计 / 备注 / 说明”做自动截断或跳过
- 保存 `sourceSheet`、`sourceRow` 便于回溯

### 7.2 PDF

适合处理：

- 打印型配送单
- 多页明细
- 页眉页脚含门店和联系人信息

建议：

- 同时保留全文文本与按页结构
- 文本模式与表格模式并存
- 对多页订单采用 `multi-page + subRule`
- 后续可增加版面块检测，提高卡片式文档命中率

### 7.3 Word

适合处理：

- 文档型订货单
- 表格 + 说明混合结构

建议：

- 同时提取段落文本和表格内容
- 优先支持 text / table 两种模式
- 对“门店信息 + 商品清单”混合文档保留 recipient 抽取规则

## 8. UI / UX 方案（鲸天系统一致性）

### 8.1 视觉基线

建议统一以鲸天系统为基准：

- **主色**：`#1677ff`
- 顶栏高度：48px
- 左侧菜单：展开 200px / 收起 60px
- 表格风格：接近 Element Plus 的密度与 hover 反馈
- 按钮语义：主按钮蓝色、危险按钮红色、次按钮白底描边
- 卡片圆角、阴影、分页、弹窗间距均保持后台系统感，而不是营销站风格

### 8.2 导入页信息架构

建议左到右 / 上到下保持如下结构：

1. 页面标题 + 面包屑
2. 步骤条：上传 → AI 分析 → 规则确认 → 解析结果
3. 左侧主工作区
   - 上传区 / 样本区 / 规则编辑区 / 结果表格
4. 右侧辅助面板
   - 文件信息
   - 解析建议
   - 字段置信度
   - 异常提示 / 规则说明
5. 底部操作区
   - 重新分析
   - 应用规则
   - 确认导入
   - 保存规则

### 8.3 交互原则

- 用户必须始终知道当前处于哪一步
- 大文件处理中必须始终有进度和状态文案
- AI 推断字段必须可见，不允许“悄悄猜”
- 解析结果中的错误 / 重复 / 缺失字段必须高亮
- 提交下单前必须有明确二次确认

### 8.4 当前项目建议调整

从现有记忆看，万能导入 V2 当前主色记录为 `#0fc6c2`，这与鲸天系统长期主色 `#1677ff` 存在偏差。  
**建议以鲸天真实系统蓝为统一基线，青绿色只作为局部强调色或成功色，不作为一级主色。**

## 9. 性能设计

这是 V2 的核心评分点之一，必须从前端、后端、数据层三侧同时设计。

### 9.1 前端性能

#### 1）Web Worker 解析大文件
适用场景：大于 500KB 或高行数文件。

目标：
- 避免主线程卡死
- 保证上传区、按钮、进度条可交互
- 支持中止解析

#### 2）虚拟列表
适用场景：解析结果 500~5000 行。

目标：
- 只渲染可视区域
- 保证滚动流畅
- 避免 React 因大数组重渲染卡顿

#### 3）防抖 / 节流
应用于：
- 搜索规则
- 过滤历史批次
- 实时校验输入
- 大表格局部编辑

#### 4）分阶段渲染
原则：
- 先出文件信息
- 再出样本预览
- 再出 AI 规则
- 最后出完整结果表

不要等待所有信息都准备好后一次性渲染。

### 9.2 上传性能

#### 小文件策略
- 直接表单上传
- 适合 10MB 以下文件

#### 大文件策略
- 2MB 分片上传
- 服务端会话合并
- 合并后统一执行解析

建议补强：
- 将当前内存会话升级为 **Redis / 临时对象存储**，避免 Vercel Serverless 实例切换导致分片状态丢失
- 增加上传会话状态查询接口，支持断点续传

### 9.3 LLM 性能

LLM 是最不稳定的一段，必须控耗时。

建议：

1. **只传样本，不传全量内容**
2. **限制样本大小**：如前 20~30 行 / 前 3000 字符
3. **先结构摘要，再规则生成**（可作为后续升级）
4. **同文件 hash 命中已存规则时跳过 AI 分析**
5. **对成功规则做缓存与复用**

### 9.4 后端性能

#### 解析执行
- 规则执行阶段必须不再调用 LLM
- 纯解析逻辑保持同步清晰、可定位
- 对 1000 行 Excel 解析目标控制在秒级

#### 入库提交
当前逐行插入虽然实现简单，但不是长期最优。

建议升级为：
- 批量插入 SQL
- 或 Prisma `createMany`
- 单批 100~500 条事务提交

这样能明显降低高并发或大批量保存时的数据库往返成本。

### 9.5 数据查询性能

建议索引：

- `import_batches(created_at)`
- `import_orders(batch_id)`
- `import_orders(order_no)`
- `parse_rules(is_active, updated_at)`

重复检测场景建议：
- 批次内重复：前端或内存 Map 即可
- 数据库重复：按 500 条分片查询是合理的，但后续可升级为临时表或更标准化批量查询方案

## 11. 接口设计建议

### 11.1 文件分析类
- `POST /api/analyze`：上传文件样本并生成推荐规则
- `POST /api/extract-sample`：仅提取样本，用于调试或规则测试
- `POST /api/rules/generate`：基于样本或文本重新生成规则

### 11.2 规则管理类
- `GET /api/rules`
- `POST /api/rules`
- `PUT /api/rules`
- `DELETE /api/rules`

### 11.3 解析执行类
- `POST /api/parse`：标准解析
- `POST /api/upload-chunk`：大文件分片上传与完成解析
- `POST /api/check-duplicates`：重复检测

### 11.4 结果持久化类
- `POST /api/import-orders`：保存导入结果
- `GET /api/import-orders?action=batches`：批次列表
- `GET /api/import-orders?batchId=...`：批次内订单

### 11.5 建议补充接口
- `GET /api/upload-chunk/status`：查询上传会话状态
- `POST /api/rules/test`：用选定规则测试单个文件
- `POST /api/rules/feedback`：记录“规则解析成功/失败/被修改”的反馈

## 12. 校验与容错设计

### 12.1 业务校验
建议保留以下原则：

- A 组：`storeName`
- B 组：`receiverName + receiverPhone + receiverAddress`
- A / B 至少满足一组
- `itemCode / itemName / quantity` 尽量识别

### 12.2 常见异常提示

- 文件类型不支持
- 样本提取失败
- AI 未返回合法 JSON
- 规则缺少 columns / regex / subRule
- 解析后无有效记录
- 存在重复单号
- 存在低置信度字段映射

### 12.3 用户提示策略

错误分三层：

1. **阻断错误**：无法继续，如文件损坏、规则非法
2. **可修正错误**：如字段缺失、映射不准，提示用户修改规则
3. **风险提示**：如低置信度推断、重复订单，仅提醒并高亮

## 13. 部署方案（Vercel）

### 13.1 部署原则

- 前端与 API 路由统一走 Next.js
- 数据库使用 Prisma Postgres / Neon
- 生产环境通过环境变量配置 AI Key、数据库地址
- 静态资源与页面由 Vercel 托管

### 13.2 Vercel 适配重点

1. **Serverless 超时控制**：LLM 分析必须限制样本大小与超时时间
2. **大文件会话问题**：内存分片会话不适合长期生产，建议迁移 Redis / Blob
3. **临时状态避免依赖单实例内存**
4. **环境变量管理**：
   - `DATABASE_URL`
   - `AI_API_KEY`
   - `AI_API_URL`（建议可配置，不要完全写死）
   - `AI_MODEL_NAME`

### 13.3 建议上线策略

- 先上线“规则确认后解析”版本
- 再逐步强化自动化程度
- 先确保 9 份考试样本可稳定通过
- 再扩展到更多真实客户文件

## 16. 结论

这套系统的正确方向，不是“让 LLM 直接把文件变成订单”，而是：

> **让 LLM 负责理解文件结构，让规则引擎负责稳定执行，让前端负责把不确定性透明化。**

对这个项目而言，真正的壁垒不在“能不能接大模型”，而在于三点是否同时成立：

1. **像鲸天系统**：业务人员愿意用
2. **能解析任意格式**：复杂场景能扛住
3. **性能够稳**：批量场景敢上线

按当前基础判断，项目已经具备较好的 V2 雏形。接下来最关键的是：

- 统一 UI 基线
- 强化规则资产化
- 补齐生产环境分片与入库稳定性
- 用标准样本做持续回归

只要把这四件事收紧，这个系统就不只是“考试项目”，而是可以继续往真实业务工具演进。
