# 万能导入 V2 开发任务清单

> 日期：2026-06-06  
> 对应方案：`docs/万能导入V2技术方案-2026-06-06.md`  
> 目标：将“万能导入 V2”拆成可执行、可验收、可排期的开发任务，便于直接进入实施。

---

## 1. 拆分原则

本清单按以下原则组织：

1. **先定基线，再做增强**：先收紧 UI、主流程、数据链路，再补性能与资产化。
2. **优先做 P0**：先解决会影响演示、验收、上线稳定性的事项。
3. **每项任务都可验收**：尽量明确产出、影响范围、验收标准。
4. **尽量贴合现有代码**：基于当前 `fee-manager` 项目已有模块继续推进，不重造轮子。

---

## 2. 当前基础判断

当前项目已经具备以下基础：

- 已有导入页主流程：上传 → AI 分析 → 规则确认 → 结果预览
- 已有规则 DSL 与 AI 规则生成机制
- 已有多种 parser.type 支持
- 已有规则管理、历史批次、重复检测
- 已有 Web Worker / 分片上传 / 虚拟列表等性能基础能力
- 已有 Vercel 部署链路

因此本轮拆分不是“从零开发”，而是：

> **围绕现有万能导入 V2，做产品化收口、架构加固和验收补强。**

- 把一级主色统一到 `#1677ff`

**重点文件：**
- `app/import/page.tsx`
- `app/components/Common/*`
- `app/components/Upload/*`
- `app/components/Orders/*`
- `app/globals.css` 或相关样式文件

**验收标准：**
- 导入页主操作按钮、步骤条、选中态、表格高亮均为鲸天蓝体系
- 页面看起来与鲸天系统其他模块风格一致，不再像独立 demo 工具

---

### Task 1.2 收紧导入页布局层级与信息密度

**验收标准：**
- 用户一眼能看懂当前在哪一步、下一步做什么

### Task 1.3 统一风险提示与状态语义

## WP2：导入主流程与交互收口

### Task 2.1 明确步骤流状态机
**优先级：P0**

**目标：** 让上传 → 分析 → 确认 → 结果 成为严格可控的流程，而不是松散页面切换。

**主要工作：**
- 定义每一步可进入条件、可返回条件、禁用条件
- 阻止用户在关键数据未完成前跳步
- 补齐“重新分析 / 重置规则 / 返回上一步”的状态处理

**重点文件：**
- `app/import/page.tsx`

**验收标准：**
- 任意步骤切换都不会出现状态错乱
- 文件、规则、结果三者始终同步

---

### Task 2.2 强化分析中与解析中的进度反馈
**优先级：P0**

**主要工作：**
- 细分“上传中 / 样本提取中 / AI 分析中 / 规则应用中 / 结果校验中”状态
- 每个状态有明确文案与进度条
- 长耗时阶段支持 loading message 与阶段说明

**验收标准：**
- 用户等待超过 1 秒时始终能看到当前系统在做什么
- 不出现“页面像卡死了”的体验

---

### Task 2.3 收紧规则确认与 JSON 编辑体验
**优先级：P0**

**主要工作：**
- 规则来源标识清晰：AI 生成 / 已保存 / 空白规则
- 提供 JSON 编辑前后的校验提示
- 非法 JSON、缺失关键结构时即时拦截
- 编辑后支持一键重新测试当前文件

**验收标准：**
- 用户修改规则后能立即知道规则是否可执行
- 规则编辑不会变成“盲改 JSON”

---

### Task 2.4 结果预览区收紧为“可确认导入”的业务视图
**优先级：P0**

**主要工作：**
- 结果表格补齐关键字段列
- 重复、无效、低置信度、缺失项高亮
- 结果顶部展示统计卡：总行数 / 有效数 / 异常数 / 重复数
- 确认导入按钮与风险提示联动

**验收标准：**
- 用户能直接依据结果页决定“是否导入”
- 结果视图不只是原始数据表，而是业务确认页面

## WP3：解析链路与规则引擎加固

### Task 3.1 统一分析阶段与执行阶段接口边界
**优先级：P0**

**主要工作：**
- 明确 `/api/analyze` 只负责生成推荐规则
- 明确 `/api/parse` 或分片完成接口只负责执行已确认规则
- 统一接口返回结构：状态、message、stats、errors、orders

**重点文件：**
- `app/api/analyze/route.ts`
- `app/api/parse/route.ts`
- `app/api/upload-chunk/route.ts`
- `lib/ai/deepseek.ts`
- `lib/parser/engine.ts`

**验收标准：**
- 分析与执行职责清晰
- 便于测试、复用、定位问题

---

### Task 3.2 补齐规则结构校验器
**优先级：P0**

**主要工作：**
- 在规则执行前增加结构合法性检查
- 校验 parser.type、必需节点、columns / regex / subRule 等关键字段
- 输出明确报错而不是运行时崩溃

**验收标准：**
- 非法规则在执行前被拦截
- 错误提示可定位到具体字段

---

### Task 3.3 统一 parser 输出标准
**优先级：P0**

**主要工作：**
- 各 parser 输出统一 `ParsedOrder[]`
- 保留 `sourceFile`、`sourceSheet`、`sourceRow`
- 统一 `validationErrors`、`extraFields` 结构

**验收标准：**
- 不同 parser.type 输出结构一致
- 结果页和入库逻辑无需为不同 parser 写特殊分支

---

### Task 3.4 增强 Excel / CSV 非标准表格容错
**优先级：P1**

**主要工作：**
- 优化空行、备注、合计、说明、分页头识别
- 强化横向矩阵和多 Sheet 兼容
- 合并单元格干扰场景做更稳妥处理

**验收标准：**
- 对复杂 Excel 的容错更高，减少用户手改规则次数

---

### Task 3.5 增强 PDF / Word 结构提取
**优先级：P1**

**主要工作：**
- PDF 保留更完整的页级文本块信息
- Word 同时保留表格与段落结构
- 为 card / text / multi-page 模式提供更好的样本输入

**验收标准：**
- PDF / Word 规则生成质量提升
- 半结构化文档的识别稳定性提升

## WP4：性能与稳定性优化

### Task 4.1 改造大文件分片状态存储
**优先级：P0**

**问题现状：** 当前 `lib/chunk-store.ts` 采用进程内内存 `Map` 保存上传会话，适合本地，不适合 Vercel Serverless 的多实例环境。

**主要工作：**
- 将上传会话从内存态迁移到可持久方案
- 方案候选：Redis / Upstash Redis / 临时对象存储 + 元数据表
- 增加会话状态查询接口
- 为断点续传预留结构

**重点文件：**
- `lib/chunk-store.ts`
- `app/api/upload-chunk/route.ts`

**验收标准：**
- 大文件上传不依赖单实例内存
- 上传会话在生产环境更稳定

---

### Task 4.2 将逐条入库改为批量入库
**优先级：P0**

**问题现状：** `app/api/import-orders/route.ts` 当前对每条 order 单独执行一次 insert，规模上来后数据库往返成本偏高。

**主要工作：**
- 改为批量插入
- 单批建议 100~500 条
- 保留错误统计能力
- 评估事务粒度与失败回滚策略

**验收标准：**
- 1000 条导入保存性能明显提升
- 批量保存逻辑稳定，不丢单、不重复写入

---

### Task 4.3 收紧前端大表格渲染性能
**优先级：P0**

**主要工作：**
- 核查 `react-window` 使用是否覆盖所有大结果表格场景
- 减少不必要的 re-render
- 对筛选、搜索、切换批次做 memo / debounce 优化

**验收标准：**
- 1000+ 行结果表滚动流畅
- 切换筛选条件不会明显卡顿

---

### Task 4.4 建立性能基线与压测脚本
**优先级：P1**

**主要工作：**
- 固化 10 条 / 1000 条 / 大文件场景压测脚本
- 记录 analyze、parse、save 三阶段耗时
- 形成性能对比基线文档

**验收标准：**
- 能快速证明优化前后差异
- 验收时有可复用证据链

---

## WP5：规则资产化与验证体系

### Task 5.1 建立规则复用命中机制
**优先级：P1**

**主要工作：**
- 基于文件 hash、文件名模式、结构签名尝试匹配已有规则
- 命中时优先推荐历史有效规则
- 未命中时再调用 AI 生成

**验收标准：**
- 同类文件重复导入时，分析耗时下降
- 规则库开始产生复用价值

---

### Task 5.2 增加规则测试台闭环
**优先级：P1**

**主要工作：**
- 选规则 → 上传文件 → 立即解析 → 对比结果
- 展示命中率、异常字段、校验失败项
- 支持保存测试记录

**验收标准：**
- 规则维护不再依赖手工猜测
- 能快速验证一条规则是否真的可复用

---

### Task 5.3 记录规则反馈数据
**优先级：P1**

**主要工作：**
- 记录规则使用次数、成功次数、失败次数
- 记录用户是否手工修改了 AI 规则
- 为规则排序、淘汰、优化提供数据基础

**建议数据字段：**
- `usage_count`
- `hit_success_count`
- `hit_fail_count`
- `last_used_at`
- `source_sample_hash`

**验收标准：**
- 后续能够知道“哪些规则真的有用”

---

### Task 5.4 建立 9 份样本回归集
**优先级：P0**

**主要工作：**
- 固定 9 份考试样本为标准回归集

- 每次改规则引擎或样本提取逻辑后自动回归

**验收标准：**
- 不再依赖人工临时验证
- 能快速证明“兼容性没有被改坏”

## 9. 我建议你下一步直接做什么

如果按最稳妥的推进方式，我建议下一步直接进入：

### 第一优先：批次 A（UI + 主流程收口）
也就是先做：

- 统一鲸天系统视觉
- 收紧导入页布局
- 收紧步骤流和进度反馈
- 收紧结果确认视图

原因很简单：

1. **见效最快**：页面很快就能“像成品”
2. **最影响观感**：这是用户第一眼感知
3. **不会破坏核心解析逻辑**：相对安全
4. **能为后续链路优化提供稳定壳子**

如果只抓一句话，那就是：

> **先把 UI 和主流程收紧，再把解析链路和生产稳定性收紧，最后再做规则资产化。**
